# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This is the Vultisig Card backend service. It has a minimal Echo HTTP server with config loading, standard middleware, a Postgres connection pool, `vault_tokens` and `vultisig_reap_mappings` tables/models, a `/health` route, a nonce-based `/auth` route that issues JWTs, and authenticated `/user`, `/account`, `/card`, `/card-3ds-challenges`, `/card-shipments`, `/card-designs`, `/card-transactions`, `/activities`, `/fraud-alerts`, and `/simulation` routes that proxy user/account/card/shipment/design/transaction/activity/fraud-alert/simulation creation/lookup to the REAP API.

## Commands

- Build: `make build` (or `go build ./...`)
- Test: `make test` (or `go test ./...`)
- Lint: `make lint` (or `golangci-lint run ./...`)
- All of the above: `make ci`
- Local Postgres: `make db-up` (docker compose, `card_backend` db on `localhost:5432`, user/pass `postgres`) / `make db-down`
- Run: `go run ./cmd/server` (requires Postgres reachable at `DatabaseURL`, or the server fails fast at startup)
- Module management: `go mod tidy`

Go version: 1.26.5 (see `go.mod`).

golangci-lint must be built with a Go toolchain >= the version in `go.mod`, or it refuses to run ("Go language version used to build golangci-lint is lower than the targeted Go version"). If `make lint` fails with that error, `brew upgrade golangci-lint`. CI pins `golangci-lint-action@v7` with `version: v2.12.2` for the same reason — v6 of the action doesn't support golangci-lint v2 at all.

## Architecture

- `cmd/server/main.go` — entrypoint. Loads config, connects to Postgres (fatal on failure), builds the Echo instance with middleware (`Recover`, `RequestLogger`, `RequestID`, `CORS`, `Secure`, `Gzip`), registers routes, starts listening on `cfg.Port`. `/health` pings the DB pool.
- `internal/config/config.go` — config loading via viper. Reads `PORT`, `DATABASE_URL`, `REAP_API_KEY`, and `REAP_ENV` (`sandbox`/`prod`, default `sandbox`) from env (defaults: `8080` and a local `postgres://postgres:postgres@localhost:5432/card_backend?sslmode=disable` for the first two) and optionally merges a `config.json` in the working directory if present; env always takes precedence via `viper.AutomaticEnv()`. `main.go` fails fast at startup if `JWT_SECRET` or `REAP_API_KEY` is unset.
- `internal/db/db.go` — Postgres connection pool via `pgxpool` (jackc/pgx v5). `Connect` opens the pool and pings it before returning.
- `internal/db/migrate.go` — `Migrate` runs idempotent `CREATE TABLE IF NOT EXISTS` DDL for the `vault_tokens` and `vultisig_reap_mappings` tables at startup (raw SQL, not a migration framework — see the `ponytail:` comment there for when to switch to golang-migrate).
- `internal/models/` — DB-backed model structs, one file per table (plain structs with `json` tags only, no ORM tags — the project uses raw SQL via pgxpool, not gorm). New DB models always go here.
- `internal/reapmapping/store.go` — Postgres-backed store for `vultisig_reap_mappings` (`models.VultisigReapMapping`). All functions take a `Querier` (satisfied by both `*pgxpool.Pool` and `pgx.Tx`), so callers can run them inside a transaction when they need to. `GetNonce`/`ClaimNonce` handle the auth nonce (see below). `GetReapUserID` returns a vault's REAP user ID (`""` if unset); `SetReapUserID` sets it, creating the mapping row on first use, and only if it isn't already set (returns `false` if it was — same atomic conditional-update pattern as `ClaimNonce`).
- `internal/reap/client.go` — thin client for the REAP API (`https://sandbox.api.reap.global` / `https://prod.api.reap.global`, chosen by `Config.ReapEnv`). `CreateUser`/`GetUser`/`UpdateEmail`/`UpdatePhoneNumber`/`CreateAccount`/`GenerateSignerMessage`/`GetAccount`/`GetAccountBalance`/`GetAccountAssets`/`ListAccounts`/`CreateCard`/`ListCards`/`GetCard`/`DeleteCard`/`UpdateCardPin`/`FreezeCard`/`UnfreezeCard`/`RevealCardDetails`/`UpdateCard3DSChallengeMethod`/`ActivatePhysicalCard`/`GetCardActivationCode`/`PushProvisionCard`/`RespondToCard3DSChallenge`/`GetCard3DSChallenge`/`CreateCardShipment`/`ListCardShipments`/`GetCardShipment`/`DeleteCardShipment`/`UpdateCardShipment`/`AddCardToShipment`/`RemoveCardFromShipment`/`SubmitCardShipment`/`ListCardDesigns`/`GetCardDesign`/`GetCardTransaction`/`ListActivities`/`ListFraudAlerts`/`ReportFraud`/`GetFraudAlert`/`RespondToFraudAlert`/`AdvanceUserApplication`/`SimulateUserApplicationStatus`/`SimulateCompanyStatus`/`SimulateAccountStatus`/`SimulateCardStatus`/`SimulateAuthorization`/`SimulateThreeDSAuthorization`/`SimulateDecline`/`SimulateClearing`/`SimulateReversal`/`SimulateRefund` send the `Authorization: Bearer` and `Reap-Version` headers and return REAP's raw status/JSON body unchanged (including non-2xx error bodies and REAP's 204-empty-body on a successful update), so callers can pass them straight through. `CreateAccount`/`CreateCard`/`SubmitCardShipment` take an `idempotencyKey` argument and forward it as the `Idempotency-Key` header verbatim — generating it is the HTTP caller's responsibility (the `/account`, `/card`, and `/card-shipments/{id}/submit` handlers require the client to send that header), not this client's; `PushProvisionCard`/`ReportFraud`/`RespondToFraudAlert`/`AdvanceUserApplication` forward it too but only when non-empty (REAP treats it as optional on those). `AdvanceUserApplication`'s request body varies by KYC method (`MANAGED_KYC`/`SUMSUB_TOKEN_SHARING`/the deeply-nested `UNIVERSAL_KYC`), so it takes and forwards raw `[]byte` rather than a typed struct. `ListAccounts` filters by `ownerId` and passes `limit`/`cursor` through as query params when set. `ListCards`/`ListCardShipments`/`ListCardDesigns`/`ListActivities`/`ListFraudAlerts` take a pre-built `url.Values` and forward it as-is — the caller sets/forces any filters (e.g. `userId`) before calling. The six `Simulate*` card-transaction methods (`SimulateAuthorization`/`SimulateThreeDSAuthorization`/`SimulateDecline`/`SimulateClearing`/`SimulateReversal`/`SimulateRefund`) all take the same `SimulateCardTransactionRequest` — its `omitempty` fields make it safe to reuse across the six even though each REAP endpoint only accepts a subset.
- `internal/service/auth.go` — `AuthService.Authenticate` backs `POST /auth`: verifies a secp256k1 signature over the client-supplied nonce, checks it against `reapmapping.GetNonce`, claims it via `reapmapping.ClaimNonce` (replay protection), and issues a JWT keyed on the vault's public key. `AuthService.RequireAuth` is Echo middleware that validates the bearer JWT and stores `*Claims` (including the vault's public key) on the Echo context under `"claims"`; it guards the `/user`, `/account`, `/card`, `/card-3ds-challenges`, `/card-shipments`, `/card-designs`, `/card-transactions`, `/activities`, `/fraud-alerts`, and `/simulation` routes.
- `internal/service/user.go` — `UserService` backs `/user`. `CreateUser` runs inside a transaction holding a Postgres advisory lock on the vault's public key (`pg_advisory_xact_lock(hashtext(publicKey))`), so two concurrent creates for the same vault can't both pass the "no REAP user yet" check and each create one in REAP; it rejects with `ErrReapUserExists` if the vault already has a REAP user ID (no REAP call made), otherwise calls `reap.Client.CreateUser` and, on a 2xx response, records the returned id via `reapmapping.SetReapUserID` before committing. `GetUser`/`UpdateEmail`/`UpdatePhoneNumber`/`AdvanceUserApplication` all resolve the vault's REAP user ID first (shared `resolveReapUserID` helper, no lock needed since they don't create anything) and return `ErrNoReapUser` if none is recorded yet, otherwise call the matching `reap.Client` method. Non-2xx REAP responses are returned as-is (no error) for passthrough to the HTTP caller.
- `internal/service/account.go` — `AccountService` backs `/account`. `CreateAccount` resolves the vault's REAP user ID via the same `resolveReapUserID` helper as `UserService` (returns `ErrNoReapUser` if none recorded) and uses it as `ownerId` when calling `reap.Client.CreateAccount`, so a vault can only create accounts owned by itself; the client-supplied `signers` (if any) are passed through unchanged. `ListAccounts` resolves the vault's REAP user ID the same way and passes it as the `ownerId` filter, so a vault only ever lists its own accounts. `GenerateSignerMessage`/`GetAccount`/`GetAccountBalance`/`GetAccountAssets` are thin passthroughs to the matching `reap.Client` method — account IDs aren't tracked per-vault, so any authenticated vault can look up any account ID it's given.
- `internal/service/card.go` — `CardService` backs `/card` and `/card-3ds-challenges`, mirroring `AccountService`'s ownership pattern. `CreateCard` resolves the vault's REAP user ID via `resolveReapUserID` (returns `ErrNoReapUser` if none recorded) and overwrites the request's `userId` with it, so a vault can only create cards for itself (the client-supplied `accountId` is passed through unchanged, same as `CreateAccount`'s `signers`). `ListCards` resolves the vault's REAP user ID the same way and overwrites the `userId` query filter with it, so a vault only ever lists its own cards; any other filters (`accountId`, `status`, `type`, `limit`, `cursor`, ...) are forwarded from the request query string as-is. All other methods (`GetCard`/`DeleteCard`/`UpdateCardPin`/`FreezeCard`/`UnfreezeCard`/`RevealCardDetails`/`UpdateCard3DSChallengeMethod`/`ActivatePhysicalCard`/`GetCardActivationCode`/`PushProvisionCard`/`RespondToCard3DSChallenge`/`GetCard3DSChallenge`) are thin passthroughs to the matching `reap.Client` method — card/challenge IDs aren't tracked per-vault, so any authenticated vault can act on any ID it's given, same as `GetAccount`/`GetAccountBalance`/`GetAccountAssets`.
- `internal/service/cardshipment.go` — `CardShipmentService` backs `/card-shipments`. Unlike `CardService`, no method enforces ownership: REAP shipments aren't tied to a vault's REAP user in REAP's schema (only to the cards inside them, and cards themselves aren't tracked per-vault either — see above), so every method (`CreateCardShipment`/`ListCardShipments`/`GetCardShipment`/`DeleteCardShipment`/`UpdateCardShipment`/`AddCardToShipment`/`RemoveCardFromShipment`/`SubmitCardShipment`) is a thin passthrough to the matching `reap.Client` method; it holds no `*pgxpool.Pool` since it never needs one.
- `internal/service/carddesign.go` — `CardDesignService` backs `/card-designs`. Designs are assigned to the project (not per-vault) by REAP out of band, so `ListCardDesigns`/`GetCardDesign` are thin passthroughs to the matching `reap.Client` method, same pattern as `CardShipmentService`.
- `internal/service/cardtransaction.go` — `CardTransactionService` backs `/card-transactions`. Transaction IDs aren't tracked per-vault, so `GetCardTransaction` is a thin passthrough to `reap.Client.GetCardTransaction`, same pattern as `CardDesignService`. There is no list-transactions endpoint in REAP's API.
- `internal/service/activity.go` — `ActivityService` backs `GET /activities` (a single route, not a group — REAP's `activities` API is list-only). `ListActivities` is a thin passthrough to `reap.Client.ListActivities`, same pattern as `CardShipmentService`/`CardDesignService`: account/card IDs aren't tracked per-vault, so no ownership filter is forced.
- `internal/service/fraudalert.go` — `FraudAlertService` backs `/fraud-alerts`. Card/transaction IDs aren't tracked per-vault, so `ListFraudAlerts`/`ReportFraud`/`GetFraudAlert`/`RespondToFraudAlert` are all thin passthroughs to the matching `reap.Client` method, same pattern as `CardShipmentService`.
- `internal/service/simulation.go` — `SimulationService` backs `/simulation`, wrapping REAP's sandbox-only test helpers for advancing application/company/account/card status and simulating card-transaction lifecycle events (authorization, 3DS, decline, clearing, reversal, refund). Every method is a thin passthrough to the matching `reap.Client` method; REAP itself rejects these calls outside a sandbox environment, so no extra gating is added here.
