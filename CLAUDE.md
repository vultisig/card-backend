# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This is the Vultisig Card backend service. It has a minimal Echo HTTP server with config loading, standard middleware, a Postgres connection pool, `vault_tokens` and `vultisig_reap_mappings` tables/models, a `/health` route, a nonce-based `/auth` route that issues JWTs, authenticated `/user`, `/account`, `/card`, `/card-3ds-challenges`, `/card-shipments`, `/card-designs`, `/card-transactions`, `/activities`, `/fraud-alerts`, and `/simulation` routes that proxy user/account/card/shipment/design/transaction/activity/fraud-alert/simulation creation/lookup to the REAP API, and an unauthenticated `POST /webhooks/reap` route that verifies and persists REAP's async webhook deliveries and best-effort pushes a client notification for the vault each event concerns.

## Commands

- Build: `make build` (or `go build ./...`)
- Test: `make test` (or `go test ./...`)
- Lint: `make lint` (or `golangci-lint run ./...`)
- All of the above: `make ci`
- Local Postgres: `make db-up` (docker compose, `card_backend` db on `localhost:5432`, user/pass `postgres`) / `make db-down`
- Run: `go run ./cmd/server` (requires Postgres reachable at `DatabaseURL`, or the server fails fast at startup)
- Module management: `go mod tidy`

Go version: 1.26.5 (see `go.mod`).

golangci-lint must be built with a Go toolchain >= the version in `go.mod`, or it refuses to run ("Go language version used to build golangci-lint is lower than the targeted Go version"). If `make lint` fails with that error, `brew upgrade golangci-lint`. CI pins `golangci-lint-action@v7` with `version: v2.12.2` for the same reason — v6 of the action doesn't support golangci-lint v2 at all.

## Architecture

- `cmd/server/main.go` — entrypoint. Loads config, connects to Postgres (fatal on failure), builds the Echo instance with middleware (`Recover`, `RequestLogger`, `RequestID`, `CORS`, `Secure`, `Gzip`), registers routes, starts listening on `cfg.Port`. `/health` pings the DB pool.
- `internal/config/config.go` — config loading via viper. Reads `PORT`, `DATABASE_URL`, `REAP_API_KEY`, `REAP_ENV` (`sandbox`/`prod`, default `sandbox`), `REAP_WEBHOOK_SECRET`, and `NOTIFICATION_BASE_URL` (default `https://api.vultisig.com/notification`) from env (defaults: `8080` and a local `postgres://postgres:postgres@localhost:5432/card_backend?sslmode=disable` for the first two) and optionally merges a `config.json` in the working directory if present; env always takes precedence via `viper.AutomaticEnv()`. `main.go` fails fast at startup if `JWT_SECRET`, `REAP_API_KEY`, or `REAP_WEBHOOK_SECRET` is unset.
- `internal/db/db.go` — Postgres connection pool via `pgxpool` (jackc/pgx v5). `Connect` opens the pool and pings it before returning.
- `internal/db/migrate.go` — `Migrate` runs idempotent `CREATE TABLE IF NOT EXISTS` DDL for the `vault_tokens`, `vultisig_reap_mappings`, `vultisig_card_ownership`, `vultisig_account_ownership`, `vultisig_user_card_ownership`, and `vultisig_reap_webhook_events` tables at startup (raw SQL, not a migration framework — see the `ponytail:` comment there for when to switch to golang-migrate).
- `internal/models/` — DB-backed model structs, one file per table (plain structs with `json` tags only, no ORM tags — the project uses raw SQL via pgxpool, not gorm). New DB models always go here.
- `internal/reapmapping/store.go` — Postgres-backed store for `vultisig_reap_mappings` (`models.VultisigReapMapping`). All functions take a `Querier` (satisfied by both `*pgxpool.Pool` and `pgx.Tx`), so callers can run them inside a transaction when they need to. `GetNonce`/`ClaimNonce` handle the auth nonce (see below); `ClaimNonce` also records the vault's `hex_chain_code` (normalized: lowercased, `0x`-stripped) on first use, rejecting the claim if a later request supplies a different value rather than overwriting it, since the chain code is constant per vault. `GetHexChainCode` returns it (`""` if unset). `GetReapUserID` returns a vault's REAP user ID (`""` if unset); `SetReapUserID` sets it, creating the mapping row on first use, and only if it isn't already set (returns `false` if it was — same atomic conditional-update pattern as `ClaimNonce`). `GetPublicKeyByReapUserID` is the reverse lookup, used by `WebhookService` to map a REAP user ID back to the owning vault.
- `internal/cardownership/store.go` — Postgres-backed store for `vultisig_card_ownership` (`models.CardOwnership`), a `card_id`-keyed table mapping each REAP card ID to the vault public key that created it. Same `Querier` pattern as `reapmapping`. `Record` inserts a card's owning vault (no-op on conflict, since REAP card IDs are unique and a conflict only happens on a caller retry); `IsOwner` reports whether a card ID is recorded as owned by a given vault (`false`, not an error, if it has no record at all); `OwnerOf` is the reverse lookup, returning the owning vault's public key (`""` if unrecorded), used by `WebhookService` to map an event's card ID back to a vault. `CardService.CreateCard` is the only writer; `CardService`'s other per-card methods, `FraudAlertService`, `ActivityService`, and `WebhookService` are readers that use it to scope card IDs to the calling vault.
- `internal/accountownership/store.go` — Postgres-backed store for `vultisig_account_ownership` (`models.AccountOwnership`), the same `account_id`-keyed-to-vault-public-key shape as `cardownership` (including the reverse-lookup `OwnerOf`), kept as its own table (rather than folded into a shared/polymorphic ownership table) so each resource type's table can be indexed/optimized independently as it grows. `AccountService.CreateAccount` is the writer; `AccountService` read methods, `CardService.CreateCard`, `ActivityService`, `SimulationService`, and `WebhookService` use it to scope account IDs to the calling vault.
- `internal/usercardownership/store.go` — Postgres-backed store for `vultisig_user_card_ownership` (`models.UserCardOwnership`), a `card_id`-keyed table mapping each REAP card ID to the REAP user ID (not vault public key) that created it, mirroring REAP's own userId-based ownership model as a separate table from the vault-keyed `cardownership`. `CardService.CreateCard` is the only writer (recorded alongside `cardownership` on the same 2xx response); nothing reads it yet — it exists to track the user↔card relationship REAP itself models, independent of the vault-facing authorization table.
- `internal/reapwebhookevent/store.go` — Postgres-backed store for `vultisig_reap_webhook_events` (`models.ReapWebhookEvent`), keyed by REAP's event id. `Record` inserts the event id/type/raw payload and reports whether it actually inserted a row (no-op on conflict, since REAP redelivers on non-2xx/timeout and may also redeliver after a successful ack); `WebhookService.HandleEvent` uses that to only push a client notification on an event id's first-time recording, never on a redelivery. `WebhookService.HandleEvent` is the only writer; nothing else reads it yet.
- `internal/reap/client.go` — thin client for the REAP API (`https://sandbox.api.reap.global` / `https://prod.api.reap.global`, chosen by `Config.ReapEnv`). `CreateUser`/`GetUser`/`UpdateEmail`/`UpdatePhoneNumber`/`CreateAccount`/`GenerateSignerMessage`/`GetAccount`/`GetAccountBalance`/`GetAccountAssets`/`ListAccounts`/`CreateCard`/`ListCards`/`GetCard`/`DeleteCard`/`UpdateCardPin`/`FreezeCard`/`UnfreezeCard`/`RevealCardDetails`/`UpdateCard3DSChallengeMethod`/`ActivatePhysicalCard`/`GetCardActivationCode`/`PushProvisionCard`/`RespondToCard3DSChallenge`/`GetCard3DSChallenge`/`CreateCardShipment`/`ListCardShipments`/`GetCardShipment`/`DeleteCardShipment`/`UpdateCardShipment`/`AddCardToShipment`/`RemoveCardFromShipment`/`SubmitCardShipment`/`ListCardDesigns`/`GetCardDesign`/`GetCardTransaction`/`ListActivities`/`ListFraudAlerts`/`ReportFraud`/`GetFraudAlert`/`RespondToFraudAlert`/`AdvanceUserApplication`/`SimulateUserApplicationStatus`/`SimulateCompanyStatus`/`SimulateAccountStatus`/`SimulateCardStatus`/`SimulateAuthorization`/`SimulateThreeDSAuthorization`/`SimulateDecline`/`SimulateClearing`/`SimulateReversal`/`SimulateRefund` send the `Authorization: Bearer` and `Reap-Version` headers and return REAP's raw status/JSON body unchanged (including non-2xx error bodies and REAP's 204-empty-body on a successful update), so callers can pass them straight through. `CreateAccount`/`CreateCard`/`SubmitCardShipment`/`PushProvisionCard`/`ReportFraud`/`RespondToFraudAlert`/`AdvanceUserApplication` take an `idempotencyKey` argument and forward it as the `Idempotency-Key` header verbatim — generating it is the HTTP caller's responsibility, not this client's; the `/account`, `/card`, `/card-shipments/{id}/submit`, `/card/{id}/push-provisioning`, `/fraud-alerts`, `/fraud-alerts/{id}/respond`, and `/user/application` handlers all require the client to send that header, even though REAP itself only mandates it on some of these endpoints and treats it as optional on the rest. `AdvanceUserApplication`'s request body varies by KYC method (`MANAGED_KYC`/`SUMSUB_TOKEN_SHARING`/the deeply-nested `UNIVERSAL_KYC`), so it takes and forwards raw `[]byte` rather than a typed struct. `ListAccounts` filters by `ownerId` and passes `limit`/`cursor` through as query params when set. `ListCards`/`ListCardShipments`/`ListCardDesigns`/`ListActivities`/`ListFraudAlerts` take a pre-built `url.Values` and forward it as-is — the caller sets/forces any filters (e.g. `userId`) before calling. The six `Simulate*` card-transaction methods (`SimulateAuthorization`/`SimulateThreeDSAuthorization`/`SimulateDecline`/`SimulateClearing`/`SimulateReversal`/`SimulateRefund`) all take the same `SimulateCardTransactionRequest` — its `omitempty` fields make it safe to reuse across the six even though each REAP endpoint only accepts a subset.
- `internal/service/auth.go` — `AuthService.Authenticate` backs `POST /auth`: verifies a secp256k1 signature over the client-supplied nonce, checks it against `reapmapping.GetNonce`, claims it via `reapmapping.ClaimNonce` (replay protection), and issues a JWT keyed on the vault's public key. `AuthService.RequireAuth` is Echo middleware that validates the bearer JWT and stores `*Claims` (including the vault's public key) on the Echo context under `"claims"`; it guards the `/user`, `/account`, `/card`, `/card-3ds-challenges`, `/card-shipments`, `/card-designs`, `/card-transactions`, `/activities`, `/fraud-alerts`, and `/simulation` routes.
- `internal/service/user.go` — `UserService` backs `/user`. `CreateUser` runs inside a transaction holding a Postgres advisory lock on the vault's public key (`pg_advisory_xact_lock(hashtext(publicKey))`), so two concurrent creates for the same vault can't both pass the "no REAP user yet" check and each create one in REAP; it rejects with `ErrReapUserExists` if the vault already has a REAP user ID (no REAP call made), otherwise calls `reap.Client.CreateUser` and, on a 2xx response, records the returned id via `reapmapping.SetReapUserID` before committing. `GetUser`/`UpdateEmail`/`UpdatePhoneNumber`/`AdvanceUserApplication` all resolve the vault's REAP user ID first (shared `resolveReapUserID` helper, no lock needed since they don't create anything) and return `ErrNoReapUser` if none is recorded yet, otherwise call the matching `reap.Client` method. Non-2xx REAP responses are returned as-is (no error) for passthrough to the HTTP caller.
- `internal/service/account.go` — `AccountService` backs `/account`. `CreateAccount` resolves the vault's REAP user ID via the same `resolveReapUserID` helper as `UserService` (returns `ErrNoReapUser` if none recorded) and uses it as `ownerId` when calling `reap.Client.CreateAccount`, so a vault can only create accounts owned by itself; the client-supplied `signers` (if any) are passed through unchanged. On a 2xx response it records the created account's ID as owned by the vault via `accountownership.Record`. `ListAccounts` resolves the vault's REAP user ID and passes it as the `ownerId` filter, while `GetAccount`/`GetAccountBalance`/`GetAccountAssets` check `accountownership.IsOwner` before calling REAP.
- `internal/service/card.go` — `CardService` backs `/card` and `/card-3ds-challenges`, mirroring `AccountService`'s ownership pattern. `CreateCard` resolves the vault's REAP user ID via `resolveReapUserID`, checks the supplied `accountId` against `accountownership.IsOwner`, and overwrites the request's `userId` with the resolved REAP user ID. On a 2xx response it records the created card's ID as owned by the vault via `cardownership.Record` and by that REAP user via `usercardownership.Record`. `ListCards` overwrites the `userId` query filter so a vault only lists its own cards. Per-card methods check `cardownership.IsOwner` first. `GetCard3DSChallenge`/`RespondToCard3DSChallenge` fetch the challenge, extract its `cardId`, and check card ownership before returning or responding.
- `internal/service/cardshipment.go` — `CardShipmentService` backs `/card-shipments`. Shipments are scoped through their cards: create/add require owned card IDs, list requires an owned `cardId` filter, and shipment ID methods first fetch the shipment, extract `cards[].cardId`, and require every card to be owned by the caller before reading, updating, deleting, removing a member, or submitting.
- `internal/service/carddesign.go` — `CardDesignService` backs `/card-designs`. Designs are assigned to the project (not per-vault) by REAP out of band, so `ListCardDesigns`/`GetCardDesign` are thin passthroughs to the matching `reap.Client` method, same pattern as `CardShipmentService`.
- `internal/service/cardtransaction.go` — `CardTransactionService` backs `/card-transactions`. `GetCardTransaction` fetches the transaction from REAP, extracts its `cardId`, and checks `cardownership.IsOwner` before returning the transaction body. There is no list-transactions endpoint in REAP's API.
- `internal/service/activity.go` — `ActivityService` backs `GET /activities` (a single route, not a group — REAP's `activities` API is list-only). REAP's only filters that identify a specific card/account on this endpoint are `accountId` and `cardId` (no `userId`/`ownerId`), so `ListActivities` requires at least one of them (`ErrMissingScopeFilter` if neither is set), strips any `userId`/`ownerId` the caller passed, and checks whichever filter is set against `cardownership.IsOwner`/`accountownership.IsOwner` before forwarding. Returns `ErrResourceNotOwned` on a mismatch.
- `internal/service/fraudalert.go` — `FraudAlertService` backs `/fraud-alerts`. Fraud alerts and card transactions both carry a `cardId` field in REAP's response, so every method resolves the relevant card (fetching the alert via `GetFraudAlert` or the transaction via `GetCardTransaction` first when the caller only gave an alert/transaction ID) and checks it against `cardownership.IsOwner` before acting: `ReportFraud` resolves `req.TransactionID`'s card; `GetFraudAlert`/`RespondToFraudAlert` resolve the alert's card; `ListFraudAlerts` requires a `cardId` or `transactionId` filter (`ErrMissingScopeFilter` if neither is set, since REAP's list endpoint has no account/user filter to fall back on). Returns `ErrResourceNotOwned` on a mismatch. A non-2xx response from the resolving REAP call (alert/transaction not found) is passed through unchanged before any ownership check runs.
- `internal/service/simulation.go` — `SimulationService` backs `/simulation`, wrapping REAP's sandbox-only test helpers. `cmd/server/server.go` only registers the group when `REAP_ENV=sandbox`. User application simulation requires the route user ID to match the caller's mapped REAP user ID; account/card status simulation and card-transaction simulations check `accountownership`/`cardownership` before calling REAP. `SimulateAuthorization`/`SimulateClearing`/`SimulateDecline`/`SimulateRefund`/`SimulateReversal` also check the optional `transactionId`'s card against `cardownership` when set, since REAP acts on that specific existing transaction (rather than always creating a new one) when it's provided — `SimulateThreeDSAuthorization` doesn't take a `transactionId`, so it's exempt. Company status simulation fails closed because PR 17 has no local company ownership mapping to check against.
- `internal/reap/webhook.go` — `VerifyWebhookSignature` verifies REAP's async webhook signature (https://docs.reap.global/webhooks/signature-verification): parses the `X-Reap-Webhook-Signature` header (`t=<unix>,v1=<hex hmac>`), rejects if the timestamp is more than 5 minutes from now, and constant-time-compares the HMAC-SHA256 of `"{t}.{raw body}"` (using the project's webhook signing secret) against `v1`. Returns `ErrInvalidWebhookSignature` on any failure. This is REAP's separate async event-delivery mechanism, not the synchronous card-authorization-request webhook (which this project doesn't handle).
- `internal/service/webhook.go` — `WebhookService` backs `POST /webhooks/reap`. `HandleEvent` verifies the raw request body via `reap.VerifyWebhookSignature`, parses the envelope's `id`/`type`/`data`, and records it via `reapwebhookevent.Record`, then calls `notifyVault` to best-effort push a client notification — resolution misses and notification-service errors are logged, not returned, since the event is already durably recorded by that point and a downstream hiccup mustn't make REAP retry it. `resolveVault` maps the event to a vault using the same ownership tables the REST handlers check: `eventSubjectIDs` extracts a `cardId`/`accountId`/REAP user id from `data` per event type (REAP's webhook payloads "match the shape of the corresponding API resource" — e.g. `CARD_TRANSACTION_CREATED`'s data is a transaction, keyed by `cardId`, while `CARD_STATUS_UPDATED`'s data is the card resource itself, keyed by its own `id`), then `cardownership.OwnerOf`/`accountownership.OwnerOf`/`reapmapping.GetPublicKeyByReapUserID` resolve that ID to a vault public key. `COMPANY_STATUS_UPDATED`, `CARD_DISPUTE_STATUS_UPDATED`, and the `CRYPTO_DEPOSIT_*` events aren't resolved yet (`ponytail:` comment on `eventSubjectIDs` — no local ownership table for company/dispute, and deposits' `accountId` shape is unverified). Once resolved, `notifyVault` looks up the vault's `hex_chain_code` via `reapmapping.GetHexChainCode` and calls `notification.Client.Notify` with `notification.VaultID(publicKey, hexChainCode)`.
- `internal/notification/client.go` — thin client for the Vultisig notification service (`POST {NotificationBaseURL}/notify`, no auth). `Notify` sends a `Request{VaultID, Type, Title, Body}`; `Type` must be non-empty (e.g. `"generic"`) since the notification service defaults an empty type to `"keysign"`, which requires keysign-only fields this project doesn't have. `VaultID(pubKeyECDSA, hexChainCode string) string` computes `SHA256(utf8(pubKeyECDSA + hexChainCode))` as lowercase hex — this must match the client SDKs' `computeNotificationVaultId` exactly (verified against its test vector in `client_test.go`), since it's how the notification service looks up which vault's devices to push to.
